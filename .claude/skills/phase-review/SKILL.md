# フェーズレビュー

`docs/workflow.md` で必須にしているレビューを実行する。  
**このレビューを通す前にフェーズ完了と言わない。**

## 手順

### 1. 先に自分で確認する

エージェントに投げる前に、これを済ませる。  
ここで落ちるものをレビューに出すと指摘が埋もれる。

```sh
pnpm check
```

出力を確認する。「通ったはず」で進めない。  
落ちていたら直してから次へ。

変更したファイルの一覧を取る。

```sh
git status --porcelain
git diff --stat
```

### 2. 観点ごとに並列でレビューを投げる

5 つの観点を**別々のエージェントに**投げる。1 つにまとめない。

| 観点 | 見るもの | 渡す docs |
| --- | --- | --- |
| 仕様の一致 | モックと specs に対して振る舞いが合っているか。抜けている状態遷移 | `docs/specs/ui.md`, `docs/mock/tree.html` |
| 正しさ | 境界値、エラー経路、並行実行、git の失敗時の扱い | `docs/specs/git-operations.md`, `docs/pitfalls.md` |
| テスト | 振る舞いを縛れているか。実装を写しただけになっていないか | `docs/testing.md` |
| 設計 | 責務の置き場所、features と shared の境界、純粋関数の切り出し | `docs/architecture.md` |
| ドキュメント | docs と実装のずれ、docs 間の重複 | `AGENTS.md`, `docs/` 全体 |

各エージェントへの依頼には必ず 4 つを含める。

1. 対象 — フェーズ番号と変更したファイルの一覧
2. 観点 — 上の表から 1 つだけ
3. 読むべき docs — 上の表の該当分
4. 報告形式 — 指摘ごとに `重要度 (高/中/低) / ファイル:行 / 何が問題か / どう壊れるか (具体的な入力と結果)`

### 3. 指摘を検証する

**推測での指摘を採用しない。**  
「どう壊れるか」が具体的に示せていない指摘は、自分で確認してから採否を決める。  
確認できなければ見送り、その理由を残す。

### 4. 反映する

- 直すものは直す。テストを足してから直す
- 見送るものは理由を書く
- 再発防止をルールか仕組みに落とす。判断基準は `AGENTS.md` の「指摘を受けたときの扱い」
- UI の指摘はモック (`docs/mock/`) にも反映する

### 5. 波及を確認する

**修正した内容が他のファイルを古くしていないかを必ず確認する。**  
仕様を直すとプランが古くなる、ADR を置き換えると他が死んだ ADR を指す、という事故が実際に起きた。

```sh
python3 scripts/check-docs.py
```

スクリプトで拾えない波及は `docs/workflow.md` の表で手で確認する。  
新しく間違えた表現は `BANNED` に足してから進む。

### 6. 記録する

- プランのチェックボックスを埋める
- `docs/plans/README.md` の状態を更新する
- 落とし穴を踏んだなら `docs/pitfalls.md` に追記する
- ルールが増えたなら `AGENTS.md` を更新する

## 報告

ユーザーには次を伝える。

- `pnpm check` の結果
- 観点ごとの指摘件数と、採用したもの・見送ったもの
- 再発防止として何をどこに書いたか
- 次フェーズに移した項目
