# テスト

## 進め方

テスト駆動で書く。

1. **Red** — 期待する振る舞いを書いたテストを 1 つ足して、失敗を確認する
2. **Green** — 通す最短の実装を書く
3. **Refactor** — テストが緑のまま整える

守ること。

- 実装を書いてからテストを後付けしない
- テストが無いコードをフェーズの完了に含めない
- 「通ったはず」で報告しない。実行した出力を確認してから完了と言う
- 落ちているテストを skip して進めない。直すか、直せない理由をプランに書く

## 層

| 層 | 対象 | ツール | 置き場所 |
| --- | --- | --- | --- |
| Rust ユニット | git 出力のパース、コマンド組み立て、キュー | `cargo test` | 実装と同じファイルの `mod tests` |
| Rust 統合 | 実際の git を叩く一連の流れ | `cargo test` | `src-tauri/tests/` |
| フロント ユニット | ツリー構築、絞り込み、並び替え、状態遷移 | Vitest | 実装の隣の `*.test.ts` |
| コンポーネント | 行の描画、インジケーター、メニューの出し分け | Vitest + React Testing Library | 実装の隣の `*.test.tsx` |
| E2E | 起動して一連の操作 | 任意 (WebDriver) | 後回し。v1 では必須にしない |

配分はテストトロフィーの形を狙う。

- **ユニットは安いので広く敷く。** Rust のパースとフロントの純粋関数。ここが壊れると全部が壊れる
- **投資の重心は統合テスト。** このアプリはロジックより「git の実物と噛み合うか」が壊れやすい
- E2E は最小限。v1 では必須にしない

1 つのテストは Arrange / Act / Assert の 3 段で書く。  
テスト名は「何がどうなるか」を日本語で書く。`it("behind があるブランチはプッシュが拒否される")` のように読める形にする。

## git を使うテスト

実物の git を使う。  
モックした git 出力だけで固めると、実際の出力形式とずれたときに気づけない。

統合テストのフィクスチャは、一時ディレクトリに実際のリポジトリを作って用意する。

- ベアリポジトリを作って origin にする
- クローンしてコミットを積む
- behind / ahead / 未コミット / 追跡ブランチが消えた状態 / ワークツリーあり、をそれぞれ作る
- テストごとに使い捨てる。ユーザーの実リポジトリには触らない

作成手順は再利用するので、ヘルパー関数にして `src-tauri/tests/support/` に置く。

## パースの方針

人間向けの出力に依存しない。  
実行時に付ける引数と環境変数は [specs/git-operations.md](specs/git-operations.md) の「共通」にまとめてある。

テスト側で守ることは 1 つ。  
**想定外の行は捨てずにエラーとして扱う。** 黙って無視すると原因が追えなくなるので、そのケースのテストを書く。

## デザイントークンのずれを検出する

`docs/mock/tree.tmpl.html` の `:root` と `src/shared/styles/tokens.css` の値が一致していることをテストで確認する。  
`tree.html` は生成物なので読まない。  
モック側だけ直して実装が古いままになるのを防ぐ。  
片方を直したらもう片方も直さないとテストが落ちる状態にしておく。
