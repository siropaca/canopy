# ADR-0022: 変更を自分で見つけて取り直す

- ステータス: 採用
- 日付: 2026-09-04
- [ADR-0009](0009-concurrency-and-refresh.md) の「状態の取り直し」に引き金を足す

## 背景

[ADR-0009](0009-concurrency-and-refresh.md) は取り直しの引き金を 2 つだけ決めた。  
起動時の初回読み込みと、アプリ自身が走らせた書き込み操作の直後。

フェーズ 4 のあと 1 週間使って、**アプリの外で git を動かすと画面が古いまま**になることが分かった。  
ターミナルでプッシュしてもツリーの `↗1` が消えない。  
他のワークツリーでコミットしても未コミットの丸が残る。

いま古い状態を直す手段は、そのリポジトリに対して何か操作を実行するか、アプリを再起動するかしかない。  
リポジトリを 11 個並べて眺めるツールなので、見えている値が古いというのは目的そのものを損なう。

## 決定

**取り直しの引き金を 3 つ足す。フェッチはしない。**  
3 つとも同じ「スナップショットの取り直し」に落とす。

| 引き金 | いつ |
| --- | --- |
| サイドバーの「更新」 | 押したとき。全リポジトリ |
| ウィンドウが前面に戻った | 隠れている状態から見える状態へ変わったとき。全リポジトリ |
| `.git` が変わった | 監視が変化を拾ったとき。変わったリポジトリだけ |

### 監視の対象

- 見るのは `git rev-parse --git-common-dir` の実パスだけ。**ワークツリーの中身は見ない**
- その下は再帰で見る。リンクされたワークツリーの `HEAD` と `index` は `worktrees/<名前>/` にある
- `objects/` の下と `*.lock` は数えない。サブモジュールの `modules/<名前>/objects/` も同じ

### まとめ方

- **何件来ても 1 回に畳む。** git の 1 操作で `.git` の中の何十ファイルも動く
- 最後のイベントから 400ms 静かになったら出す
- 最初のイベントから 2 秒経ったら、静かになっていなくても出す
- **自分が走らせた操作の分は捨てる。** 取り直しは操作の側が既にやっている ([ADR-0009](0009-concurrency-and-refresh.md))
- 実行中のリポジトリは取り直さない。判定はフロント側
- **ウィンドウが隠れている間に届いた分も捨てる。** 戻ったときに全件読み直す

### 依存

`notify` を追加する。macOS では FSEvents を使う。

## 理由

- **3 つとも要る。** `.git` の監視だけでは、監視が張れていないリポジトリと、
  ファイルを編集しただけの未コミットが拾えない。前面復帰だけでは、
  ウィンドウを見たままターミナルで操作したときに変わらない。手で押す手段は最後の逃げ道
- **フェッチしない。** ターミナルで操作した結果を映すのが目的で、リモートに聞きに行く必要は無い。
  自動でネットワークを触ると、機内や VPN 切断のときに 11 本が 75 秒ブロックする
  ([ADR-0009](0009-concurrency-and-refresh.md) の「ネットワーク操作の打ち切り」)
- **ワークツリーの中身を見ない。** `node_modules` を抱えるので、再帰で見ると監視の対象が数十万件になる。
  代わりに、ファイルを編集しただけの未コミットは次の引き金まで反映されない。
  ステージすれば `index` が動くので拾える
- **`objects/` を数えない。** フェッチ 1 回で数千件書かれる。refs が動くまで画面は変わらないので、
  refs の側で拾えば足りる
- **`*.lock` を数えない。** git が本体と対で作る。本体の方で拾える
- **静穏だけでなく上限も置く。** 静穏だけだと、長いフェッチの間じゅう締め切りが後ろへ延びて、
  終わるまで 1 回も出ない
- **自分の分を捨てる理由は無駄の削減。** 操作の直後の取り直しは同じロックの中で走っていて、
  監視が拾った分をもう一度走らせると、同じリポジトリの読み取りが 2 倍になる。
  捨てる範囲は「操作の間 + 終わってから 1.5 秒」。イベントは FSEvents の遅延と
  まとめの分だけ遅れて届くので、操作の終了と同時に解くと取りこぼす
- **読み取りは捨てなくてよい。** git に渡す環境変数に `GIT_OPTIONAL_LOCKS=0` が入っているので、
  `git status` が `index` を書き直さない ([ADR-0009](0009-concurrency-and-refresh.md))。
  入っていないと、取り直しが `index` を書いて、それがまた取り直しを呼ぶ

## 検討した他の案

| 案 | 採らなかった理由 |
| --- | --- |
| 一定間隔で全リポジトリを取り直す | 11 リポジトリ分の git が定期的に走る。実測でローカルの読み取りだけで CPU 491% まで行く ([ADR-0009](0009-concurrency-and-refresh.md))。何も変わっていないときに走るのが大半 |
| 前面に戻ったときだけ取り直す | ウィンドウを見たままターミナルで操作する使い方が拾えない。それがいちばん多い |
| 手で押す「更新」だけ入れる | 「押さないと古い」を覚えておく必要がある。古いことに気づけないのが元の困りごと |
| ワークツリーの中身も監視する | `node_modules` を抱えるので現実的でない。監視の上限に当たるか、CPU を食う |
| `.git` の変化で**フェッチ**まで走らせる | ネットワークを勝手に触る。VPN 切断時に固まる。behind の更新は明示的なフェッチで足りる |
| git の hook で知らせる | ユーザーのリポジトリにファイルを置くことになる。他人の設定を書き換えるツールにはしない |
| 変わったファイルから、取り直す範囲を絞る | `refs/heads/x` が動いたらそのブランチだけ、のような最適化。スナップショットは 1 リポジトリ単位で組み立てているので、部分更新の経路を新設することになる。得られるのは数百 ms |
| まとめずに 1 イベント 1 回で取り直す | git の 1 操作で数十件飛ぶ。そのたびに全部の git が走る |
| 自分の操作の分もそのまま取り直す | 操作の直後の取り直しと二重になる。同じリポジトリの読み取りが 2 倍 |

## 影響

- `notify` が依存に増える。監視の失敗は握りつぶさず stderr に出す。**監視が張れなくても起動はする**
- リポジトリを追加・削除したら監視の対象を張り直す
- サイドバーに「更新」が増える ([../specs/ui.md](../specs/ui.md) の「サイドバー」)
- イベントが 1 つ増える (`repos_changed`)。フロントは変わったリポジトリだけ取り直す
- ファイルを編集しただけの未コミットは、次の引き金まで反映されない。**これは仕様**
- **猶予の 1.5 秒に外で起きた変化は落ちる。** 操作の直後にターミナルでコミットすると、
  その分は `.git` の監視では拾えない。「更新」か前面復帰まで待つことになる
- **ウィンドウが隠れている間は `.git` の変化で取り直さない。** 見ていない間に git を
  何本も起こさないため ([ADR-0011](0011-residency.md))。戻ったときに全件読み直すので取りこぼさない
