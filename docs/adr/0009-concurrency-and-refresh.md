# ADR-0009: 並行モデルと状態の取り直し方

- ステータス: 採用
- 日付: 2026-08-21
- [ADR-0006](0006-serial-queue-per-repo.md) を置き換える

## 背景

ADR-0006 は「リポジトリごとに直列、リポジトリ間は並列」を決めたが、次の 3 点が未定義だった。

- Rust 側をどの並行モデルで書くか
- 状態の取り直し (スナップショットの再取得) をいつ、どこで行うか
- 一括フェッチの結果をどう返すか

ADR-0006 の「読み取りはキューを通さなくてよい」は、書き込み中の読み取りを許してしまう点で誤りだった。

## 決定

### 並行モデル

- Tauri コマンドはすべて `async fn` にする。同期コマンドは書かない
- 子プロセスは `tokio::process::Command` を使う。`std::process::Command` は使わない
- キューのキーは**リポジトリ id ではなく `git rev-parse --git-common-dir` の実パス**。リンクされたワークツリーを別々に登録しても、ref store を共有しているので同じキューに入れる
- キューはそのキーごとの `tokio::sync::Mutex`、全体の同時実行数は `tokio::sync::Semaphore` で絞る
- 一括フェッチの同時実行上限は、全体の上限より小さくする。対話操作の枠を空けておく

### コマンドの契約

- **git の非ゼロ終了は失敗ではなく結果として返す。** `Ok(CommandResult { ok: false, ... })`
- `Err` はアプリ側の異常だけに使う。プロセスの起動失敗、パスが消えている、設定の読み書き失敗
- 操作コマンドの戻り値は `{ result: CommandResult, snapshot: RepoSnapshot }` の 1 つにする。フロントが 2 回目の invoke を投げる形にしない

`Err` で git の失敗を返すと、Tauri は 1 値しか運べないので stdout / stderr が消える。  
「失敗しました」だけ出てコンソールに何も残らない状態になる。

### 排他の粒度

- 同一リポジトリ内は**書き込み排他・読み取り共有** (RwLock 相当)
- 読み取り同士は並列でよい。書き込み中の読み取りは待たせる

`GIT_OPTIONAL_LOCKS=0` はロックの競合を避けるだけで、内容の整合性は守らない。  
フェッチが refs を書き換えている途中で `for-each-ref` を読むと、リモートに 7 コミット来ているのに `behind` が 0 のまま表示される。  
「フェッチしたのに ↙ が出ない」という再現しにくい不具合になる。

### ネットワーク操作の打ち切り

- 共通の環境変数に `GIT_SSH_COMMAND="ssh -o ConnectTimeout=5 -o BatchMode=yes"` を追加する
- フェッチとプッシュには 30 秒のタイムアウトを付け、超えたら子プロセスを kill する
- 同一リポジトリの同種操作は投入時に重複排除する。フェッチの連打で 11 本積まれない
- アプリ終了時に実行中の子プロセスを kill する

`GIT_TERMINAL_PROMPT=0` はパスワード入力待ちを防ぐが、SSH の TCP 接続には効かない。  
全リポジトリの remote が SSH なので、VPN 切断や機内では 1 本あたり 75 秒前後ブロックする。  
その間キューが詰まって、チェックアウトも実行されない。

### 同時実行の上限

読み取りとネットワーク操作で別の上限を持つ。  
実測でローカルの読み取りだけで CPU 491% (5 コア飽和) まで行くので、全部同時に投げない。

| 種類 | 上限 |
| --- | --- |
| 読み取り (スナップショット取得) | 4 |
| ネットワーク (フェッチ・プッシュ) | 4 |

### 実行中の扱い

実行中はそのリポジトリの操作系 UI を無効にする。**これは v1 に入れる。**  
ADR-0006 は「実行中の表示は v1 では持たない」としていたが、楽観的更新をしない設計と組み合わせると操作のフィードバックがゼロになり、ユーザーが同じ操作を繰り返す。  
スピナーは出さない。無効化と行を薄くするだけ。見せ方は [../specs/ui.md](../specs/ui.md)。

### 状態の取り直し

- 書き込み操作のあと、**成否に関係なく**対象リポジトリのスナップショットを取り直す
- 取り直しは、その操作と**同じ直列区間の中**で行う。書き込みの直後に、同じロックを持ったまま実行する
- `RepoSnapshot` にリポジトリごとの単調増加する `revision` を持たせる。Rust 側で採番する。フロントは自分が持っているものより古い `revision` を捨てる

一括フェッチ (11 並列、数秒) の最中にチェックアウトすると、checkout の再取得が先に返って、その後に**フェッチ開始前に読まれた**古いスナップショットが到着して上書きする。  
`revision` が無いとツリーの現在ブランチが元に戻り、次の操作まで直らない。
- キューを通さない読み取りは、起動時の初回読み込みと、ユーザーが明示的に更新したときだけに限る

### 一括フェッチ

- フロントから 11 本の invoke を並列に投げる形にはしない
- Rust から `repo_snapshot_updated` イベントを emit して、返ってきた順にフロントが差し替える
- capability に `core:event:default` を許可する

## 理由

- Tauri のコマンドに `async` を付けないとメインスレッドで動く。同期の子プロセス実行を置くと、起動時の読み込み中にウィンドウが固まる
- `std::sync::Mutex` のガードは `await` を越えて保持できない (`!Send`)。同期の Mutex でキューを書くとコンパイルが通らず、設計をやり直すことになる
- 失敗時こそ状態がずれる。`git checkout X && git pull --rebase` で checkout が成功して pull が競合で止まったとき、取り直さないと画面は元のブランチのままになる。実態は X の rebase 中
- rebase 中は `git branch --show-current` が空を返す。書き込みと読み取りが同時に走ると、現在ブランチが一瞬消える
- invoke の解決順は発行順と一致しない。`revision` が無いと古いスナップショットが新しいものを上書きし得る

## 検討した他の案

| 案 | 採らなかった理由 |
| --- | --- |
| 同期コマンド + `spawn_blocking` に寄せる | 呼び出しごとにスレッドを起こす。一括フェッチで枯渇する |
| 取り直しを成功時だけ行う | 失敗したときに画面と実態がずれる。一番困る場面で守れない |
| 取り直しをキューの外で行う | 書き込み中の読み取りで不整合な値を読む |
| 一括フェッチを 1 本の invoke で返す | 返ってきた順に差し替えられない。全部終わるまで何も出ない |

## 影響

- `src-tauri/src/queue/` は tokio 前提で書く。テストも tokio のランタイム上で書く
- `RepoSnapshot` に `revision` が増える。フロントは差し替え時に必ず比較する
- イベントを使うので、フロント側にイベント購読の層が必要になる
- 一括フェッチ中でもユーザーの操作が待たされないことを、フェーズ 2 の完了条件で確認する
